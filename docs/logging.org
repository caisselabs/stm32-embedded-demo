* Binary Logging

The demo uses CIB's binary logger. Log strings never appear in the
executable: each call site sends a catalogued 32-bit string ID (plus any
runtime arguments) encoded per the MIPI Sys-T spec. The IDs are assigned at
build time and the text is recovered off-target by a decoder.

** How the build is wired

The catalogue is produced by CIB's ~gen_str_catalog~ CMake function, which
needs a *library* to inspect. So the application is split:

- ~demo_lib~ (~src/app.cpp~) --- all the real code, including every log call
  site.
- ~demo~ (~src/main.cpp~) --- a stub whose ~main~ just calls ~app_run()~. It
  must contain no log call sites.

~gen_str_catalog~ then:

1. runs ~nm -uC~ over ~libdemo_lib.a~. The undefined symbols are exactly the
   ~catalog<...>()~ / ~module<...>()~ specializations the logger needs, and
   the string data is carried in their template arguments.
2. generates ~build/log_strings.cpp~ --- one-line functions returning the
   assigned IDs --- which is compiled into ~demo_log_strings~ and linked into
   ~demo~. LTO inlines them away.
3. generates ~build/log_strings.json~ and ~build/log_strings.xml~, the
   collateral a decoder uses to turn IDs back into text.

*** LTO and ~nm~

The ARM toolchain file selects ~arm-none-eabi-gcc-{ar,ranlib,nm}~ rather than
the plain binutils. We build with ~-flto~, so object files hold GIMPLE instead
of a normal symbol table; plain ~nm~ reports *no symbols at all*, which would
silently produce an empty string catalogue. The ~gcc-*~ wrappers load the LTO
plugin and see the symbols.

** Where the logs go

~src/logging/log_config.hpp~ specializes ~logging::config<>~ with
~logging::binary::config{app_log::log_destination{}}~.

Every translation unit that logs must include this header --- not
~<log/log.hpp>~ --- so that all of them see the same specialization. Two TUs
seeing different specializations is an ODR violation.

The destination is currently a circular buffer of 32-bit words in RAM
(~app_log::buffer~). There is no log transport on the board yet; replace
~log_destination::operator()~ with a UART/SWO writer when there is one, and
nothing else has to change.

~logging::binary::log_writer~ wraps each destination call in
~conc::call_in_critical_section~, so logging from an ISR is safe given
~hal::concurrency_policy~.

** Using it

#+begin_src cpp
#include <logging/log_config.hpp>

auto f() -> void {
    CIB_LOG_MODULE("app");          // scopes the module ID for this scope
    CIB_INFO("Booting");
    CIB_WARN("The answer is {}", x);
}
#+end_src

Arguments known at compile time are formatted at compile time; only runtime
arguments are sent along with the ID.

CIB's flow machinery logs at ~TRACE~, so ~flow.start(...)~ / ~flow.end(...)~
entries appear in the catalogue for free.

** Tooling

Two host-side tools. Both decode the same packets with the same code --- CIB's
~mipi_messages.py~ --- and differ only in where the bytes come from.

| tool                  | reads                             | when                            |
|-----------------------+-----------------------------------+---------------------------------|
| ~tools/unwrap_log.py~ | a GDB dump of ~app_log::buffer~   | target halted under the debugger |
| ~tools/logmon~        | a serial port, or a saved capture | target running                  |

They compose: ~unwrap_log.py~ emits a bare packet stream, which is exactly what
~logmon --replay~ expects, so a ring-buffer dump can be viewed in the TUI:

#+begin_src sh
python3 tools/unwrap_log.py --input log.bin > ring.bin
python3 tools/logmon --replay ring.bin --catalog build/log_strings.json
#+end_src

*** Offline: dumping the ring buffer

Dump the whole buffer --- header included --- from GDB, flatten it, and run it
through CIB's decoder:

#+begin_src sh
# in gdb, after halting the target
(gdb) dump binary value log.bin app_log::buffer

# on the host, in one line
python3 tools/unwrap_log.py --input log.bin | \
    python3 <cib>/python/cib/log_decode.py \
        --input /dev/stdin --json build/log_strings.json
#+end_src

~<cib>~ is the CPM checkout, ~build/_deps/compile-time-init-build-src~. The
decoder handles Short32, Short64 and Catalog messages.

~unwrap_log.py~ writes the packet stream to stdout by default and keeps its
progress line on stderr, so the two chain directly. ~log_decode.py~ takes a
filename rather than reading stdin, hence ~/dev/stdin~; bash process
substitution works equally well if that reads better:

#+begin_src sh
python3 <cib>/python/cib/log_decode.py --json build/log_strings.json \
    --input <(python3 tools/unwrap_log.py --input log.bin)
#+end_src

Pass ~--output ordered.bin~ to keep the flattened stream around instead.

One wrinkle with the pipe form: the shell reports only the last command's
status, so a failure in ~unwrap_log.py~ (bad magic, truncated dump) still
exits 0 --- the decoder simply sees an empty stream. The diagnostic is on
stderr either way, but use ~set -o pipefail~ if the exit code is being
checked.

**** Why not dump ~app_log::buffer.words~ directly

The decoder reads packets back-to-back: no framing, no end marker, no length
outside the packets themselves. That makes the raw ring unusable in two ways,
and ~tools/unwrap_log.py~ exists to fix both.

1. *Trailing zeros abort the decode.* A dump of the ring includes every
   unwritten word. The decoder takes the first zero word's low nibble as a
   message type and raises ~Unknown message type: 0~. The real entries print
   first, so this looks survivable, but it exits non-zero and truncates
   anything downstream.
2. *A wrapped ring is out of order.* Once ~total_words > capacity~ the oldest
   surviving word sits at index ~total_words % capacity~. Every word is still
   a valid packet, so this does /not/ error --- it silently prints the log with
   a seam in the middle, which is the worse failure.

~unwrap_log.py~ reads ~capacity~ and ~total_words~ out of the header, emits
exactly the live words oldest-first, and reports on stderr how many were
overwritten before the dump was taken. That last number is the reason to dump
the header rather than slicing the array in GDB --- it is the only indication
that packets were lost.

The ~magic~ field ('CIBL') is checked, so dumping ~app_log::buffer.words~ by
mistake is reported rather than silently mis-parsed.

Slicing in GDB works too if the header is not wanted, but note that ~words~ is
a ~std::array~ and no pretty-printer is loaded, so it has to go through the
underlying member:

#+begin_src sh
(gdb) dump binary value log.bin app_log::buffer.words._M_elems[0]@app_log::buffer.total_words
#+end_src

**** Truncated final packet

The ring is written a word at a time, so halting the target midway through a
multi-word packet leaves a partial one at the end and the decoder runs off the
end of the file. Not reachable while every call site is a single-word Short32,
but it becomes possible as soon as something logs with runtime arguments.

*** Live: monitoring over serial

~tools/logmon~ reads the packet stream off the target's serial line and
decodes it as it arrives.

#+begin_src sh
# live, with the TUI
python3 tools/logmon --port /dev/ttyACM0 --catalog build/log_strings.json

# plain stdout, and keep the raw bytes for later
python3 tools/logmon --port --plain --capture session.bin \
    --catalog build/log_strings.json

# replay a capture (or an unwrap_log.py output) with no board attached
python3 tools/logmon --replay session.bin --catalog build/log_strings.json
#+end_src

The TUI needs textual --- from PyPI (~pip install 'textual>=0.52'~), not from
the distro: Ubuntu 24.04's ~python3-textual~ is 0.1.13 and predates every
Textual API the TUI uses, so it imports and then fails. Without textual the
tool says so and falls back to ~--plain~. Serial reading needs pyserial
(~python3-serial~). Keys: ~space~ pause, ~c~ clear, ~q~ quit.

Pause freezes the view without losing anything: records keep being drained off
the reader thread into a bounded holding buffer and are appended on resume, so
a pause taken to read something does not silently drop what arrived meanwhile.
The buffer is capped at the same row limit as the table, so a long pause on a
chatty target cannot grow without bound --- and a ~--capture~ file has
everything either way.

~--catalog~ takes the ~log_strings.json~ matching the running firmware. The
file is re-read when its mtime changes, so a rebuild is picked up without
restarting the monitor.

**** Layout

| module               | role                                                  |
|----------------------+-------------------------------------------------------|
| ~logmon/cib.py~      | finds and imports CIB's ~mipi_messages.py~            |
| ~logmon/catalog.py~  | loads ~--catalog~ JSON; re-reads it when mtime changes |
| ~logmon/decode.py~   | byte stream to records: alignment, resync, counters   |
| ~logmon/sources.py~  | ~SerialSource~ (pyserial), ~FileSource~ (replay)      |
| ~logmon/cli.py~      | argument handling and ~--plain~ output                |
| ~logmon/tui.py~      | the Textual app                                       |

~cib.py~ locates the CIB checkout by reading
~CPM_PACKAGE_compile-time-init-build_SOURCE_DIR~ out of ~CMakeCache.txt~,
because the path moves depending on whether ~CPM_SOURCE_CACHE~ was set when
the project was configured. ~BUILD_DIR~ overrides which build tree is
consulted and ~CIB_PYTHON~ points straight at the directory holding
~mipi_messages.py~.

One implementation note worth knowing before editing ~decode.py~: a packet's
length is not knowable up front. A Catalog message's length depends on the
argument list looked up from its ID, and CIB's message classes pull bytes off
an iterator without reporting how many they took. A small counting iterator
wrapper is what tells the buffer how far to advance.

The reader runs on a worker thread and pushes records onto a queue that the UI
drains on a timer. Decoding on the event loop instead would let a chatty target
starve the UI --- at 115200 the target can emit a packet roughly every 350us,
far faster than a sensible repaint rate.

**** Command line

| flag                | meaning                                                     |
|---------------------+-------------------------------------------------------------|
| ~--port [PORT]~     | serial port; bare ~--port~ means ~/dev/ttyACM0~             |
| ~--replay FILE~     | read a saved stream instead of a port                       |
| ~--catalog FILE~    | ~log_strings.json~ matching the running firmware            |
| ~--baud N~          | default 115200; must match the firmware's USART2 setting    |
| ~--capture FILE~    | tee every received byte, for a later ~--replay~             |
| ~--align N~         | 0-3, or ~auto~; defaults to ~auto~ for a port, 0 for a replay |
| ~--plain~           | print to stdout instead of starting the TUI                 |
| ~--replay-delay S~  | pause between replay chunks, to pace the UI                 |

Capture whenever a session might be worth a second look: it costs nothing and
turns any oddity into something reproducible off the bench.

**** Reading an unframed stream

The target writes packets to the wire as bare little-endian words: no
delimiter, no length, no sync marker. That decodes fine from a known packet
boundary --- which a RAM dump is --- but a live line is not so tidy, so
~logmon/decode.py~ recovers on its own:

- *Byte alignment.* Attaching mid-word leaves every following word out of
  phase. ~detect_alignment()~ scores all four offsets by how many packets each
  decodes cleanly and picks the winner. ~--align 0..3~ forces one.
- *Resync.* An undecodable packet advances the buffer by one word rather than
  one byte: with raw words, packet boundaries are word-aligned once the byte
  alignment is right. The bad word is shown as a hex dump rather than
  swallowed.
- *Incomplete vs corrupt.* CIB's decoder raises the same ~ValueError~ for "ran
  off the end of the buffer" as for a bad packet. They are told apart by
  whether the decode consumed everything available; a packet still undecodable
  past ~MAX_PACKET_BYTES~ is judged corrupt, so an unknown ID cannot stall the
  stream forever.

A stale catalog is the common cause of undecodable packets: the ID is real but
absent from the JSON, and since a Catalog packet's length depends on its
argument list, an unknown ID cannot even be skipped by length. Watch the error
counter in the status bar.

If the link turns out to be noisy, the fix is framing on the target (COBS with
a 0x00 delimiter makes resync exact rather than heuristic). ~decode.py~ is the
only module that would change.


*** Tests

| file                             | covers                                             |
|----------------------------------+----------------------------------------------------|
| ~tools/test/test_unwrap_log.py~  | ~unwrap_log.py~ --- 25 tests                       |
| ~tools/test/test_logmon.py~      | everything under ~logmon~'s UI --- 15 tests        |

~test_unwrap_log.py~ checks ring-model equivalence across capacities and wrap
points, the CLI contract the pipeline depends on (packets on stdout, progress
on stderr, non-zero exit on a bad dump), and end-to-end runs through the real
~log_decode.py~ that pin both failure modes described above.

~test_logmon.py~ covers catalog loading and hot-reload, chunk-boundary
handling (arbitrary splits, and one byte at a time --- the serial case),
partial packets held rather than dropped, resync after corruption, unknown IDs
reported rather than fatal, the undecodable-tail cap, and all four byte
alignments. Two are worth calling out:

- A *pty test* opens a real tty pair with ~os.openpty()~ and drives the actual
  pyserial path, so the serial source is exercised without a board.
- A *property test* injects seeded-random corruption and asserts the decoder
  never emits a message that was not in the catalog. Corruption may lose
  packets; it must never invent them.

~TuiTest~ drives the Textual app headlessly through Textual's own test pilot:
a replay landing as rows, undecodable words appearing rather than killing the
app, the row cap trimming oldest-first, pause holding and then draining, byte
alignment resolved in the UI, and the status bar's markup rendering as style
rather than literal text. These reach APIs the decoder tests never touch ---
~DataTable.remove_row~, worker threads, the pause path --- so a Textual
upgrade that moves one of them fails here instead of at the bench. They skip
themselves when ~logmon.tui~ will not import --- textual missing, or a textual
too old to have what it imports.

~tools/CMakeLists.txt~ registers both with ~add_unit_test(... PYTEST ...)~,
which names them ~PYTHON.unwrap_log_test~ and ~PYTHON.logmon_test~ in ctest and
hooks them into the ~python_tests~ target:

#+begin_src sh
cmake -B build -G Ninja
ctest --test-dir build                   # C++ and Python tests together
ctest --test-dir build -R '^PYTHON\.'    # just these
ctest --test-dir build -E '^PYTHON\.'    # just the C++ tests
ninja -C build python_tests              # or as part of a build
#+end_src

CI splits the suite by prefix --- the compiler matrix and the sanitizer jobs pass
~-E '^PYTHON\.'~, and one ~tool_tests~ job passes ~-R '^PYTHON\.'~ --- and every
ctest invocation passes ~--no-tests=error~, so a job that registers no tests
fails instead of quietly passing.

The infrastructure runs them with ~pytest -n auto~, so pytest and pytest-xdist
have to be installed; ~tools/CMakeLists.txt~ announces and skips them if pytest
is missing rather than breaking the default build. Both files are plain
~unittest~, so they also run with no pytest at all:

#+begin_src sh
python3 -m unittest discover -s tools/test -v
#+end_src

Cases needing CIB's decoder skip themselves until the project has been
configured once. Set ~BUILD_DIR~ if the build tree is somewhere other than
~build/~ or ~build-host/~.

Two groups depend on optional packages --- ~TuiTest~ on textual, ~SerialPtyTest~
on pyserial --- and skip when they are absent. That is right for a bare
checkout and wrong for CI, where it would quietly shrink the suite by seven
tests and still report success. The ~tool_tests~ job installs both and sets
~LOGMON_REQUIRE_OPTIONAL=1~, which turns a missing package into a failure
naming it. The guard reads the same flags the skips do, so the two cannot
drift apart.

** Version logging

~app_log::version_config~ supplies ~CIB_LOG_VERSION()~. ~version_string~ is
deliberately empty --- a non-empty one makes the encoder emit a MIPI "long
build" message, which puts the string in the image (defeating the point) and
hands the destination a byte span rather than a word span.

~CIB_LOG_VERSION()~ is not on the boot path: it emits a MIPI Build message
(type 0), which the bundled ~log_decode.py~ does not decode.

** Stable string IDs

IDs are assigned per build, so a decoder needs the ~log_strings.json~ from the
matching build. To keep them stable, copy a build's ~log_strings.json~ into the
source tree and feed it back:

#+begin_src cmake
gen_str_catalog(
  ...
  STABLE_JSON ${CMAKE_CURRENT_SOURCE_DIR}/log/stable_strings.json
)
#+end_src

Matching strings keep their previous IDs; new ones get fresh IDs.
