
* API Reference

** Exclusive Region

- header: ~shared/region.hpp~

This facility serializes access through an exclusive region. Multiple senders can request access concurrently; the region ensures only one executes at a time. Waiters are queued in FIFO order without dynamic allocation.

Every entry point is templated on a compile-time string ~Name~ that uniquely identifies the exclusive region. Each distinct ~Name~ produces an independent region with its own queue.


*** ~region::within~

#+begin_src cpp
template <stdx::ct_string Name, async::sender S>
auto within(S &&s) -> async::sender auto;
#+end_src

Returns a sender that acquires the region, runs ~s~, then releases the region. This is the primary interface.

The returned sender completes with ~s~'s value channel — values from ~s~ flow through the ~release~ to the downstream receiver unchanged.

Models ~region::acquire<Name>() | seq(s) | region::release<Name>()~.

**** Example

#+begin_src cpp
auto s1 = calc_a() | region::within<"hw_bus">(send_data) | start_detached();
auto s2 = calc_b() | region::within<"hw_bus">(send_data) | start_detached();
#+end_src

Imagine the results of `calc_a` and `calc_b` are sent in the value channel. `send_data` will receive the data and send it out the hardware, one byte at a time. The data must be sent as a set. Sending the data from `calc_a` and `calc_b` on the hardware at the same time will result in corrupted data. `region::within<"hw_bus">` ensures that only one `send_data` will be executing at a time.


*** ~region::acquire~

#+begin_src cpp
template <stdx::ct_string Name>
auto acquire();
#+end_src

Returns a pipeable adaptor. ~upstream | region::acquire<Name>()~ produces a sender that runs ~upstream~, then acquires the region, and finally re-emits ~upstream~'s values on the value channel. A downstream like ~then([](int v){...})~ sees the value that was on the wire before acquire.

If the region is free, acquire completes immediately. If the region is busy, the sender is enqueued and suspends until the current holder calls ~release~.

#+begin_quote
Don't be a monster, prefer ~within~ over manually pairing ~acquire~ and ~release~.
#+end_quote


*** ~region::release~

#+begin_src cpp
template <stdx::ct_string Name>
auto release();
#+end_src

Returns a pipeable adaptor. ~upstream | region::release<Name>()~ runs ~upstream~, then releases the exclusive region. If a sender is waiting for the exclusive region, it hands ownership off to the longest waiting sender; otherwise the region is now free.

For ~upstream | region::release<Name>()~, ~release~ will pass through the values generated by upstream.

#+begin_quote
Don't be monster, prefer ~within~ over manually pairing ~acquire~ and ~release~.
#+end_quote


*** Free Black Eye

The ~region~ facility can be great or it can be a poke-in-the-eye.

The a waiting sender will run in the context of the ~region::release~. In the world of hardware, this is most often what you want... but this can be surprising.

An example will help (we are going to use the primitives to make it clear... don't use the primitives, use ~within~ like a sophesticated user):


#+begin_src cpp
  auto wait_done = continue_on(trigger_scheduler<"wait_done">{});

  auto s1 = a | region::acquire<"a">() | load_hw() | wait_done | region::release<"a">() | b;
  auto s2 = c | region::acquire<"a">() | load_hw() | wait_done | region::release<"a">() | d;

  start_detached(s1);
  start_detached(s2);

  void on_irq42() { triggers<"wait_done">.run(); }
#+end_src

Let's say ~s1~ acquires the exclusive region first. Conceptually, ~s2~'s ~load_hw~ is first in the FIFO for the exclusive region.

  1. ~s1~ ~load_hw~ completes (imagine this is a ~then~).
  2. ~s1~ ~wait_done~ schedules on the ~trigger_scheduler<"wait_done">~ and the context returns.
  3. In our isolated little example here, nothing else is happening.
  4. IRQ 42 fires and ~on_irq42~ is called from the ISR context.
  5. From the ISR context, ~s1~ ~release~ is called.
  6. The ~release~ logic will notice that a sender is queued and waiting for the exclusive region.
  7. From the ISR context, ~s2~ ~load_hw~ is started and completes.
  8. From the ISR context, ~s2~ ~wait_done~ schedules on the trigger scheduler.
  9. From the ISR context, ~b~ is started.

There isn't anything unique or special about this behaviour, but it could be surprising. When you are doing hardware activities like trying to keep a buffer full for a slow serial communication port (i2c, spi, ...), this is exactly what you are looking for.

If you need to control the context more carefully, ~continue_on~ right after the ~acquire~:

#+begin_src cpp
  auto s1 = a | region::within<"a">( continue_on(S) | stuff ) | b;
#+end_src
